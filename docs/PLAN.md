## Implementation notes

Decisions made while building, which take precedence over the plan text below:

- **Solution file** is `Grably.slnx` (the .NET 10 default format), not `Grably.sln`.
- **Tests** use xUnit v3 on Microsoft.Testing.Platform, opted in through `global.json`. The filter syntax is xUnit's, not VSTest's: `dotnet test --solution Grably.slnx --filter-not-trait "Category=Desktop"` (or `--filter-trait` to run only the desktop tests).
- **Win32 interop** is generated by Microsoft.Windows.CsWin32 from `src/Grably.Platform/NativeMethods.txt`; add API names there instead of writing `DllImport`s.
- **Package versions:** Microsoft.Extensions.* stay on the 10.0.x line to match the .NET 10 runtime, even though 11.0 packages exist.
- **H.NotifyIcon:** `TaskbarIcon.ForceCreate()` turns on Windows Efficiency Mode by default, which throttles the whole process; always call `ForceCreate(enablesEfficiencyMode: false)`.
- **Default hotkey conflict:** on the development machine `Alt+PrintScreen` (capture active window) is already registered by another app (Win32 error 1409). Registration failures are logged and kept in `HotkeyController.Registrations` so the M4 settings page can show them.
- **Isolated runs:** setting `GRABLY_HOME` puts settings, data and logs under one folder; tests, DevCli checks and end-to-end runs use it so the real profile is never touched.
- **Region capture finishes on mouse release** by default (like Snipping Tool). Resize handles, arrow-key nudging and Enter/double-click confirmation are the optional `screenshot.adjustBeforeCapture` setting; the recording overlay (M7) will use that mode. Clicking without dragging captures the hovered window, or the monitor when no window is under the pointer.
- **Full-screen capture** takes the monitor under the pointer. **Window capture** crops the frozen desktop to the foreground window's visible frame, so anything covering that window is included (what you see is what you get).
- **Overlay logic** lives in `Grably.Core/Capture/RegionSelection` (unit-tested state machine); the WPF overlay only draws it and feeds it physical pointer positions from `GetCursorPos`.
- **End-to-end checks** drive the real app with `grably-dev send-keys`, `wait-window` and `mouse` (which refuses to click unless a named Grably window is visible). Verified on a two-monitor 100 %/125 % setup: a drag across the monitor seam captures the exact pixel area.
- **Overlay pointer positions** come from each mouse event (`PointToScreen`), not `GetCursorPos`: a late-handled mouse-down otherwise starts the selection where the cursor has moved to (found by the M3 end-to-end run).
- **Editor logic** lives in `Grably.Core/Annotations/AnnotationEditor` (tools, gestures, selection, z-order, styles, crop, undo), unit-tested without WPF. The WPF `EditorCanvas` draws and forwards input; one `AnnotationRenderer` draws both the screen and the export.
- **Projects are created on first save,** not at capture time: until the image is annotated, the saved PNG is itself the original. A `.grably` zip holds `original.png`, `document.json` and `project.json` (the flattened image's path). `Grably.exe <file>` opens an image or project in the editor (forwarded to the running instance).
- **Blur and pixelate** are computed in Core (`ImageFilters`) from the original pixels, so redaction never reveals other annotations and re-renders identically.
- **Soft shadow** is drawn as three offset, very transparent copies of the shape (no bitmap effects), so it is identical on screen and in exports.
- **Last-used style per tool** is kept in `settings.editor.toolStyles` and saved when an editor closes.
- **Never losing or misplacing work:**
  - Tray Exit asks every edited editor first (`CloseCoordinator`) and aborts on Cancel, because WPF ignores Cancel during `Shutdown`.
  - Windows sign-out keeps unsaved annotations in their projects without asking.
  - Save only overwrites captures, Save as results, and project image paths inside a screenshots folder or recorded by Grably's own projects.
  - An opened image file is never overwritten: its first save is a Save as.
- **End-to-end scripts** live in `tests/E2E` (scratch copies get wiped between sessions). Run them after changes to capture or the editor.
- **Library** (`Grably.Core/Library/LibraryRepository`): SQLite with WAL and `PRAGMA user_version` migrations; a newer schema than the app knows is refused rather than guessed at. Search is an FTS5 external-content table over title, app, window title and OCR text, kept in step by triggers; each search word is a prefix match. File paths are unique (case-insensitive). An item has a file, a project, or both: annotations kept at sign-out for an image Grably may not overwrite become a project-only item.
- **`LibraryService`** keeps the library in step with captures, editor saves and kept projects, and owns the 360x240 JPEG thumbnails. Library failures are logged and never fail a capture or a save; opening the database is retried on the next use, and a damaged database (found on opening by `PRAGMA quick_check`, or by a query error) is moved to `library.db.broken-*`. A new library, on first run or after that, is filled from disk (`LibraryScanner`): every project (which records its image) and every image in the screenshots folders, so no annotations become unreachable. It only ever deletes thumbnails inside its own folder.
- **Library actions:** Delete sends the image to the Recycle Bin, then its project once the image is gone; for a file that cannot be recycled (network share, removable drive) Windows asks before destroying it, and an item whose image is kept keeps its project and stays in the library. An item open in an editor cannot be renamed or deleted. Rename also updates the project's image path and is undone if the library cannot be updated. The grid checks files in the background (network folders can be slow), keeps the selection across refreshes and shows up to 20,000 items.
- **After a capture** the options are: open the editor (default), a corner preview (`CapturePreviewWindow`: edit, copy, show in folder, drag the file out; it hides after 7 s unless the pointer is on it), or only copy and save.
- **Settings** edit a copy (`AppSettings.Clone`) until Save, which writes only the sections the window shows (`WithWindowSectionsFrom`) so changes made elsewhere meanwhile, such as editor tool styles, survive. While a shortcut box is listening Grably's own hotkeys are released (`HotkeyController.Suspend`), so pressing PrintScreen there records it instead of capturing; after recording the box stops listening. A shortcut needs Win, or two of Ctrl, Alt and Shift (one being Ctrl or Alt), unless its key is PrintScreen, Pause, Scroll Lock or F13-F24 (`HotkeyGesture.IsSafeAsGlobalHotkey`), so it can never take a letter, Ctrl+C or Alt+F4 from other apps. Save reports duplicate shortcuts and shortcuts another app owns; a taken PrintScreen shows a hint with a button to Windows' keyboard settings. Recording settings arrive with recording (M7).
- **Start with Windows** is the HKCU Run value `Grably` (`"<exe>" --background`). Settings only writes it when the choice changes, so saving settings from a development build never repoints an installed Grably's entry.
- **OCR** (`Platform/Text/OcrService`) uses `Windows.Media.Ocr` in the user's profile languages. Windows OCR misses text in tall, mostly empty images long before its 10,000-px limit (a 10,000-px strip with one line returns nothing), so `Core/Text/OcrLayout` reads every image in overlapping strips of at most 2,000 px, enlarges narrow images 2x strip by strip, and keeps each line from the one strip that owns its centre. Recognised text is never logged.
- **Text features:** Capture text picks an area (the overlay with its own hint, `RegionSelection.Hint`) and copies its text. The editor's Copy text (Ctrl+Shift+C) reads the original image inside the crop, not the annotations. `TextIndexer` reads library screenshots in the background, newest first. It reads each file into memory and closes it at once, so saves, renames and deletes never wait on it, then decodes it with Windows imaging: whole up to 16 Mpx, strip by strip beyond. It stores `ocr_text` (empty means read, nothing found) only if the item has not changed since it was read. An editor save clears the text so it is read again. `screenshot.makeTextSearchable` turns it off. OCR calls are serialized strip by strip, so a user's text capture never waits long behind indexing.
- **Scrolling capture** (`ScrollingCaptureService`) turns the wheel over the centre of the picked area. After each turn it waits for the area to change (apps repaint late) and then to settle. It adapts the number of notches so each step moves about half the area, waits for held modifier keys (Ctrl or Shift would zoom or scroll sideways), and stitches off the UI thread.
- **`Core/Imaging/ScrollStitcher`** compares rows on a band of columns without the scrollbar strip. Rows count as the same only when nearly every pixel matches: sampled columns made lines that differ in one digit ("Line 001", "Line 004") look identical, so sticky bands grew into the content and the capture stopped after one step (found in review; `ScrollStitcherTextTests` covers it with rendered text). A quick search on sampled columns proposes offsets, and full rows confirm them. A match tolerates up to 15 % differing rows (a hover highlight, a caret) and ignores single-colour rows, preferring the expected distance when repeating content allows several. Sticky headers and footers appear once.
- **Scrolling capture endings:** the bottom of the page (no movement twice), Esc or Stop, the pointer leaving its resting spot, a held key, repeated mismatches (it steps back and halves the step first), or 30,000 px. Early endings are explained in a notification. The status panel sits outside the area and is excluded from capture (`SetWindowDisplayAffinity`).
- **Known limit:** apps that scroll by fractional device pixels (browsers at 125 % scaling) re-render text slightly differently at each position. Such pages may stitch with mismatches, to be checked in the M11 hardening pass.
- **ffmpeg** (until M10) was the LGPL v3 shared build `n9.0.2-39-g7adfbe40dc` from the FFmpeg-Builds month-end release of 2026-10-31, pinned in `tools/fetch-ffmpeg.ps1`; that script stays for quick developer setups. Since M10 the shipped one is Grably's own minimal build (see "Minimal ffmpeg" below). Either is copied next to `Grably.exe`, `grably-dev` and the tests. `FfmpegLocator` uses it, an explicit override, or PATH only with `GRABLY_FFMPEG_ALLOW_PATH=1`.
- **Encoders** are chosen by a real 5-frame encode at the output size (`EncoderProbe`), in the order NVENC, QSV, AMF, Media Foundation, then HEVC, then smaller sizes. OpenH264 was dropped from the plan's list: Cisco's patent licence covers only Cisco's own binaries, not one built into ffmpeg, and Media Foundation (part of Windows) is the licensed software fallback. On the development machine NVENC and AMF are listed but fail, and QSV wins. Quality options come from `ffmpeg -h encoder=...` (QSV `-global_quality`, Media Foundation quality mode, OpenH264 a bitrate from the pixel rate).
- **Recording engine** (`Platform/Recording`):
  - Capture: Windows.Graphics.Capture copies each frame into its own texture.
  - Compositor: a thread draws frame N at time N / fps with Direct2D (crop, scale, letterbox).
  - Readback: the GPU video processor converts to NV12 (BT.709, limited range); BGRA is read back when it cannot.
  - Writing: a buffer pool of about 128 MB feeds ffmpeg's stdin. Late frames are repeated (`FramePacer`), and when the encoder falls behind the newest frame is repeated instead of read back, so the duration always matches the clock.
  - Output: a Matroska intermediate in `sessions/{id}`, remuxed to MP4 with `+faststart`.
- **COM and WinRT interop** for capture is in `WinRtInterop.cs`: function pointers on the COM vtables (IGraphicsCaptureItemInterop, IDirect3DDxgiInterfaceAccess) and a raw-pointer `CreateDirect3D11DeviceFromDXGIDevice` import. CsWin32's projection would hand back its own COM types where the device is a Vortice object.
- **Licensing of the shipped ffmpeg (settled in M10):** the FFmpeg-Builds package bundles about 40 libraries whose licences would need notices and, for LGPL and MPL parts, source. Grably ships its own minimal LGPL build instead (below).
- **Recorder robustness:**
  - Stop never hangs: a writer stuck on a full pipe gets ffmpeg killed, and what was written stays playable.
  - Dispose joins the worker threads before freeing GPU objects.
  - A capture callback racing Dispose is a no-op.
  - The recorder raises `Failed` when ffmpeg dies mid-recording.
  - A failed start leaves no orphaned ffmpeg and no "recording" session.
  - Odd sizes are cropped by a pixel, never resampled.
  - Window titles go into the session only, never the log.
- **Capture exclusion works for layered WPF windows** (checked first, as planned, by `grably-dev exclusion-test`): `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` keeps both layered and opaque windows out of GDI screenshots and Windows.Graphics.Capture recordings. So the control bar, countdown and area outline are ordinary WPF windows; the outline also sits just outside the area.
- **Recording clock** (`Core/Recording/RecordingClock`): one pausable clock on the performance counter in 100-ns ticks, the unit of WASAPI's packet timestamps. The frame pacer runs on it, and every audio packet is placed on the timeline by its own capture timestamp (`AudioTimeline`). Gaps (loopback sends nothing during silence, a device switch) become silence, drift beyond 20 ms drops the overlap, and packets captured during a pause are left out. This replaces the plan's end-of-recording drift correction: tracks are already on the clock.
- **Audio** (`Platform/Recording/AudioCapture`): NAudio 3.3's `WasapiRecorder`, whose packets carry the QPC timestamp. Tracks are forced to 48 kHz stereo float (Windows converts) and written raw (`*.f32`), so a crash loses nothing and there is no 4 GB limit. The microphone follows the default device through Windows stream routing; loopback reopens when the default output changes (checked every second). Mute writes silence. A source that cannot start becomes a warning, and the recording goes on.
- **Mux:** video stream-copied, tracks mixed with `amix normalize=0` and a limiter, AAC 192 kb/s, `apad` + `-shortest` so the video decides the length, `+faststart`.
- **Sync, measured with `grably-dev synctest`** (a white flash and a 1 kHz beep at the same recording times, from a generated track that travels the same path as WASAPI packets):
  - 10 s: audio 1 to 9 ms from video.
  - With a 2-second pause: the pause is left out of the duration and sync is unchanged.
  - The real WASAPI latency on speakers is a manual check.
- **Recording flow** (`App/Recording/RecordingController`):
  - Picking: the overlay picks the target. A clicked window is recorded as a window (followed if it moves), a whole screen as a monitor, anything else as a region on one screen.
  - Before recording: the pre-record bar has PC sound, microphone with a live level, fps, Record and Cancel. The countdown runs while the encoder is probed, so recording starts the moment it ends.
  - While recording: the control bar has the timer, pause, mute, stop and discard. The pause hotkey is registered only while recording, and the tray shows the recording icon.
  - When stopped: the MP4 is saved to the videos folder (`Grably_yyyy-MM-dd_HH-mm-ss.mp4`) and added to the library with a thumbnail and duration, the session folder is removed, and the trim editor opens on it.
  - Interrupted recordings: sessions with a video but no saved MP4 are offered at startup (save, delete, or ask again).
  - Library: recordings open in the trim editor, GIFs in the default viewer.
- **Interruptions and errors:**
  - Exit asks to stop and save a running recording. Sign-out closes the recording files properly; the recording is offered back at the next start.
  - The recovery prompt has explicit Save / Delete / Later buttons, and Delete uses the Recycle Bin.
  - A saved session records its `outputPath` before it is removed, so it is never saved twice.
  - An audio source that fails to start, or a failed output-device switch, becomes a warning instead of aborting the recording or crashing Grably (the switch is retried every second).
  - A failure after the recorder started stops and saves it, never leaving it running invisibly.
  - Discard pauses while it asks.
- **Audio timestamps:** a packet with no or an absurd timestamp is taken to end now. Quiet tracks are filled with silence as time passes (up to 300 ms behind), never in one huge write when sound returns.
- **Settings merge** became value by value (`AppSettings.WithChangesFrom`): the Settings window applies only what it changed, so pre-record bar choices made while it was open survive.
- **Recording visibility:** the screenshot overlay and the corner preview are also excluded from capture, so a screenshot taken mid-recording is not in the video. WPF-UI's styles gave plain windows a minimum size, which made the small panels (scrolling capture, preview, recording bars) far too big; they now set `MinWidth`/`MinHeight` to 0.
- **Cursor effects:**
  - `Core/Recording/EffectTimeline` keeps clicks and keys on the recording clock: a ring grows for 550 ms; a caption shows for 1.6 s and fades for the last 0.3 s, and typed letters build a word.
  - The pointer highlight is a ring, so the pointer keeps its colours.
- **Keys never leak typed text:** `KeystrokeFormatter` ("shortcuts only") takes what the user's own keyboard layout types for the key (`KeyText`, from `ToUnicodeEx` with flag 4 so dead keys still work). It shows only Ctrl/Alt/Win chords and keys that never type. Anything that types text, anything with AltGr (right Alt, which Windows reports as Ctrl+Alt: AltGr+Q is @ on German keyboards), numpad keys and Alt codes are left out. Found in review: a US-only key list let these through.
- **Input comes from Raw Input, not hooks** (`Platform/Input/InputMonitor`): a message-only window with `RIDEV_INPUTSINK` on its own thread, used only while a recording with clicks or keys runs.
  - Raw Input is told after the fact: nothing the user does waits for Grably. Low-level hooks would stall input during a GC pause, and Windows silently removes hooks that time out.
  - Held modifiers are followed from the input stream itself (left and right separately), since asking the keyboard later is wrong for quick shortcuts.
  - Keys count only while the window in front overlaps what is recorded, and clicks only inside it.
  - Keys are never logged.
- **Overlays** (`Platform/Recording/OverlayRenderer`) are drawn by the compositor in Direct2D, mapped from screen pixels through the capture's crop and scale. A window target's frame is read each frame with one DWM call, outside the GPU lock, so effects follow a moving window. DirectWrite comes with `Vortice.Direct2D1` (there is no separate 3.x package).
- **Webcam:**
  - `WebcamSource` uses WinRT `MediaCapture` with a BGRA frame reader, at least 24 fps and up to 1280x720.
    - Alpha is forced opaque, padded rows are packed, and three buffers are reused in turn.
    - It falls back to shared access when another app has the camera.
    - Any failure leaves the camera out with a clear message (privacy permission, in use) and never stops the recording.
  - The camera opens with the pre-record bar, so the bubble can be placed before recording and does not delay the start.
  - The same frames feed the on-screen `WebcamBubble` and the compositor. The bubble is a mirrored circle or rounded rectangle in three sizes, draggable and excluded from capture. The compositor draws the picture centre-cropped into a geometry mask where the bubble is.
- **Testing without the user's devices:** `grably-dev effects-test` records the test pattern with scripted pointer, click and shortcut input and a generated camera picture (`SyntheticWebcam`), then checks each effect in frames from the video. A real camera is a manual check: Grably never turns it on by itself.
- **Measured on the development machine (Intel QSV, 3440x1440 at 125 %):** 30 fps native with no drops and 9.5 ms per frame; 60 fps native with 1 late frame in 8 s; the BGRA fallback keeps up at 30 fps after 3 start-up drops. Test-pattern colours come back within 2 levels on both paths. Captures have no yellow border: borderless capture is granted to the unpackaged app.
- **UI snapshots** for the Library, Settings and the empty Library use throwaway sample data in a temporary folder, never the user's library: `--ui-snapshot Library|LibraryEmpty|Settings|SettingsConflict`. `--ui-snapshot Trim` makes a 12-second test video with a tone (needs the bundled ffmpeg) and shows it with two edits, a selection and the playhead on an exact frame.
- **Trim editor** (`App/Trim`):
  - Edits are an `EditList` (Core) of kept parts in the recording's own time. Trimming, cutting and moving a handle each return a new list, so undo and redo walk a list of versions. The recording file is never changed. Saved edits reopen as one step on top of the whole recording, so undo still brings back what was cut.
  - A trim handle dragged outwards brings that end back (`EditList.WithEnds`); cuts in between stay.
  - Edits and the playhead snap to frame starts (`VideoFrames`). When paused, the preview is the exact frame from ffmpeg: seeked a quarter of a frame early, a BMP through a pipe, at most 1600 px wide, the last 30 kept. So what is on screen is exactly where an export cuts. While scrubbing, the newest wanted frame is decoded next and the ones passed over are skipped.
  - Playback uses `MediaElement`, followed every 15 ms; it jumps over a removed part when the next tick would land in it, so removed frames do not show. If Windows cannot play the file, the window still steps through it frame by frame.
  - Closing the window stops its ffmpeg work (frames, thumbnails, sound wave), so the video is free for a rename or delete at once.
  - The timeline's thumbnails (keyframes only past two minutes) and sound wave (square-root scale, so quiet sound shows) are made by ffmpeg each time the video opens.
  - Edits are saved after every change in `<local>/trims/<hash of the path>.json`. They are ignored when the video's length has changed, follow a rename in the library, and are deleted with the video.
  - A recording opens in the trim editor when it is saved and from the library. "Edit this frame" sends the full-size frame to the image editor as a new picture.
  - Decoded pictures are copied out of their decoder (`BitmapConversion.Decode`): a frozen `BitmapFrame` still belongs to the thread that decoded it, and cropping it on the UI thread throws.
- **Export** (`Platform/Recording/VideoExporter`):
  - Always re-encoded: each kept part goes through `trim`/`atrim`, then `concat`, so cuts are exact to the frame. MP4 uses the probed encoder and AAC. GIF gets its own palette (`palettegen` in diff mode, Bayer dithering) and has no sound.
  - The picture is cut half a frame before each edit, between two frames. Recordings pass through Matroska, whose time stamps are whole milliseconds, so frame 1 sits at 0.033 s, before 1/30 s; cutting at the exact time started a third of all cuts one frame late (found in review). Sound is cut at the exact times.
  - Exports go next to the recording as `..._edited.mp4` or `.gif` and join the library; GIFs are listed as GIF items.
  - Progress comes from `-progress pipe:1`. The file is written as `name.mp4.part` and renamed when complete, so a crash or sign-out never leaves a broken video under the real name. Cancelling, closing the window or quitting kills ffmpeg at once and removes the part; closing or quitting during an export asks first, and sign-out stops it without asking.
  - Checked with `grably-dev export`: exports of the test video and of a QSV test-pattern recording are the kept length to the millisecond, at full size and 720p, and GIFs decode. The test video is made through Matroska like a recording, and each part of an export starts on exactly the recording's frame at its cut, including cuts on frames 1, 31 and 277.

- **Minimal ffmpeg** (`tools/ffmpeg/build.sh`, run in Docker by `tools/ffmpeg/build.ps1` and in the release workflow):
  - The unmodified FFmpeg 9.0.2 release, cross-compiled with MinGW-w64 in a digest-pinned `ubuntu:24.04` image. Every source is pinned: SHA256 for tarballs, commits for git tags.
  - Configured with `--disable-everything --disable-autodetect`, LGPL 2.1 or later. It enables only:
    - the hardware and Media Foundation encoders
    - AAC, MPEG-4 (test videos), PNG, BMP and GIF
    - Matroska, MP4, GIF and image pipes
    - the filters, lavfi sources and bitstream filters Grably uses
  - Its extra libraries are permissive:
    - zlib and libvpl, linked in statically
    - nv-codec-headers 12.2 (NVIDIA drivers from 550; newer headers would need newer drivers) and AMF headers 1.5.2 (the minimum for ffmpeg 9)
    - the MinGW runtime, linked statically, so only Windows system DLLs are imported. The script fails if anything else is.
  - 14 MB instead of about 180 MB, so the installer went from 145 MB to 86 MB. Licences (including the MinGW-w64 runtime's) and `BUILD.txt` (versions, configure line) ship next to it.
  - The build records its script's SHA256 (`BUILD-SCRIPT.sha256`). `build.ps1` reuses a build only while `build.sh` is unchanged, and `pack.ps1` refuses one made by another version of it.
  - Anything new Grably asks of ffmpeg must be added to the lists in `build.sh`. Building it showed two gaps:
    - the lavfi test sources need the `wrapped_avframe` decoder
    - the `metadata` filter links against libavformat without declaring it, so `grably-dev synctest` now reads brightness from `showinfo` instead of `signalstats`
  - All checks pass on it: encoders (QSV and Media Foundation here), `record --pattern` colours, `export --sample` with frame-exact cuts, GIF, `synctest` with a pause (within 1 ms), `effects-test`, the unit tests and the Trim snapshot.
- **Packaging** (`build/pack.ps1`):
  - A self-contained win-x64 publish, with LICENSE and the notices, packed by Velopack (`vpk` 1.2.161, a local dotnet tool).
  - The package id `SBLAdvisory.Grably` installs to `%LocalAppData%\SBLAdvisory.Grably`, away from Grably's data folder, with a Start menu shortcut only. Uninstalling never touches the user's library.
  - The script refuses the developer ffmpeg (`-AllowDevFfmpeg` only for local tries).
- **Updates** (`App/Shell/UpdateService`):
  - `VelopackApp.Build().Run()` runs first in `Main`. Its uninstall hook removes the start-with-Windows entry.
  - Velopack's own install-at-startup is off. A downloaded update is installed only once the single-instance lock is held (`UpdateService.InstallPendingAtStartup`). Found in review: otherwise a second launch, which only hands its arguments to the running Grably, would swap the files under it mid-recording.
  - Checks run 30 seconds after startup, then every 12 hours (30 minutes after a failure) while the setting is on, and on request from the tray and from Settings (About).
  - A newer version downloads in the background. The tray item then becomes "Restart to update to X". It runs the usual exit questions (recording, unsaved editors, exports), then hands the update to Velopack's updater, which installs it and restarts Grably in the background. If the user doesn't restart, it installs at the next start. The "ready" balloon is never shown during a recording.
  - `GRABLY_UPDATE_FEED` points updates at a folder or URL instead of GitHub Releases, for testing. Failures are logged and shown only when the user asked.
- **Release** (`.github/workflows/release.yml`, on a `v*` tag matching `<Version>`):
  - The ffmpeg job builds the minimal ffmpeg.
  - The tag is checked against `<Version>` first.
  - The Windows job:
    - builds and tests
    - runs the fresh ffmpeg through `grably-dev export --sample` as a GIF (MP4 too when the runner has an H.264 encoder)
    - downloads the previous release for a delta (none for the first release)
    - packs and uploads a draft release
    - attaches the exact FFmpeg source tarball (LGPL) and only then publishes. A failed step stops it, and a re-run can finish a half-made release.
  - `ffmpeg.yml` rebuilds ffmpeg and runs the same check on pull requests that change its build script.
- **Checked with `tests/E2E/install.ps1`:**
  - Setup installs 0.1.10, which starts, finds 0.1.1010 in a local feed and downloads it.
  - Starting it again installs 0.1.1010 first.
  - Uninstalling removes the app, the shortcut, its Installed apps entry and its start-with-Windows entry, and leaves the user's data. The script puts back a developer's own start-with-Windows entry.
  - A silent Setup does not start the app; a normal one does.
- **About** in Settings says Grably uses FFmpeg under the LGPL and has a Licenses button that opens the installed `THIRD-PARTY-NOTICES.md`.
- **SBL colours and credit (1.0.1, #28):**

- **Hardening (M11).** The manual checks of PRs #4 to #22 are collected in [RELEASE-CHECKLIST.md](RELEASE-CHECKLIST.md), and what could be automated was. Two defects turned up and are fixed:
  - **A closed window did not end its recording.** The recording ran on with its last picture until stopped by hand. Windows' capture-item Closed event did not arrive when the recording was started from a thread without a message loop. `ScreenCaptureSource` now also checks every 250 ms that the window still exists. `grably-dev window-test` records its own test window while it grows, is minimised, restored and closed: it ends 0.17 s after the close, keeps the minimised stretch, and shows the picture throughout.
    - Found in review: a window closed while recording was still starting was reported before anyone listened. The controller now checks `IsSourceClosed` right after subscribing. A close after Stop or Discard no longer claims the recording was saved, and a listener failing on the timer thread can no longer crash Grably.
  - **A crash a few seconds into a recording left an empty file.** The Matroska muxer kept up to five seconds (a cluster) in memory, and the start of the file in its write buffer. The recording now closes a cluster every second and flushes after every packet (`-cluster_time_limit 1000 -flush_packets 1`), so a crash loses about a second. `grably-dev recovery-test` kills a recording mid-way and saves it as the startup offer does: 3.2 of about 4 seconds come back.
  - **OCR:** the self-test now reads dark-theme, small, dim and button text. White text on a blue button at 12 px loses punctuation ("0.1.5" as "O. 1.5"); 13 px and up is read correctly. Grey contrast-stretched input and 3x enlargement did not help (3x made it worse), so neither was kept.
  - **Copy text** reads only the crop (`EditorService.TextSource`, unit-tested).
  - **Library:** recordings show a play mark with their length, and GIFs show "GIF".
  - **README:** screenshots rendered by Grably itself (`--ui-snapshot LibraryShowcase|Editor|Trim`, `tools/readme-images.ps1`), never from the screen.
  - **Encoders above 4096 px:** on this Intel machine QSV H.264 fails, and Grably picks Media Foundation's software H.264 before hardware HEVC, as planned. Whether it keeps up on a real 5K monitor is on the checklist; `bench --pattern` cannot tell, because its own GPU work is the limit at that size.
  - **Measured with a projector driver active:** recording was much slower (12 to 25 fps at 1920x1200) than in M6, with the old ffmpeg as well. This is on the checklist rather than changed.

## The plan

Audience: the Opus agent that will implement this, working mostly unattended from a terminal in `d:\repos\grably`.

### Context

Grably is a new Windows 11 desktop app for taking screenshots, annotating them (arrows, shapes, text, blur and so on) and recording the screen to video, in the spirit of TechSmith Snagit/Camtasia. The repo (`https://github.com/SBL-Advisory/grably`) contains only a one-line `README.md`, so everything is greenfield. The goal of v1 is a free, open source (MIT), installable app with auto-update that a normal user can rely on daily for capture, annotate, record, trim and share.

Machine facts checked on 2026-11-14: .NET SDK 10.0.402 (and 9.0.306), Visual Studio 2022 and 18, Node 24, ffmpeg on PATH (a gyan.dev full build - GPL, includes libx264, must not be what tests or the shipped app use). No Rust. The dev machine is Intel-only graphics (QSV, no NVENC/AMF hardware) with a 3440x1440 display, so local runs exercise the QSV and software encoder paths only.

A design review with web lookups and local benchmarks was done on 2026-11-14; its findings are folded in below. Points it could not confirm are marked "verify".

### How to work

**Process.** Follow the user's `change-workflow` skill for every milestone (issue -> branch `<issue#>-<slug>` -> implement -> `code-review` skill -> version bump -> commit -> push -> PR written with `gh-pr-desc`, never merge, never commit to `main`). One deviation, approved by the user on 2026-11-14: branches are **stacked**. The first milestone branches from `main` with PR base `main`; every later milestone branches from the previous milestone's branch tip and its PR base is that previous branch, so each PR shows only its own milestone. Do not wait for merges, do not force-push, and fix earlier-milestone bugs on the current branch rather than rewriting older branches. Say in each PR body that the stack should be merged bottom-up with merge commits (squash-merging a stack causes conflicts above it).

**Writing rule.** The user's global rule: never use the em dash character anywhere (code, comments, UI strings, commits, issues, PRs, docs). Use " - ".

**Persist the plan.** In M1 copy this plan to `docs/PLAN.md` with a milestone checklist and tick items off as PRs open, so a fresh session can resume from the repo alone. Also create a project `CLAUDE.md` with build, test, run and DevCli commands.

**Verify APIs instead of trusting memory.** Several libraries have moved on (NAudio is at 3.x, WPF-UI at 4.x, Velopack 1.x, Vortice 3.x). Before using an API from one of them, read the package's XML docs or current README. Use the latest stable versions compatible with `net10.0`, pinned through central package management.

**Self-verification is a design requirement.** The agent cannot watch the screen, so every engine feature must be drivable from a console harness and checkable from files:
- `tools/Grably.DevCli` (console app, not shipped) exposes each capability as a command (list in "Verification").
- Check videos with `ffprobe -of json`, pull frames with `ffmpeg -ss T -i x.mp4 -frames:v 1 f.png` and look at them with the Read tool.
- `Grably.exe --ui-snapshot <Window> --out file.png` (Debug only) opens a window with sample data, renders its root visual with `RenderTargetBitmap`, saves and exits, so layouts can be reviewed as images.
- Anything that still needs a human goes into a "Manual checks" list in the PR body.

Libraries: CommunityToolkit.Mvvm, Microsoft.Extensions.Hosting (DI + lifetime), Serilog (rolling file), WPF-UI (Fluent windows, controls and compile-checked `SymbolIcon` names), H.NotifyIcon.Wpf (tray), Vortice.Direct3D11 / DXGI / Direct2D1 / DirectWrite, NAudio (WASAPI), Microsoft.Data.Sqlite, Velopack. All are MIT or Apache-2.0.

Cross-cutting rules:
- **Coordinates.** All capture geometry is in physical pixels of the virtual desktop (`PixelRect`, `PixelPoint` in Core). Convert to WPF DIPs only at the view boundary. App manifest declares PerMonitorV2 DPI awareness and Windows 10/11 `supportedOS`.
- **Target framework.** Windows-specific projects use `net10.0-windows10.0.26100.0`. Never use a `.1` revision of the Windows TFM: that opts into the CsWinRT 3 preview, which drops the `As<I>()` helper the capture interop relies on. Keep all WinRT/COM interop for capture in one file (`WinRtInterop.cs`) so it is easy to fix in one place.
- **Data locations.** Settings `%AppData%\Grably\settings.json`. Library DB, thumbnails, editable projects, recording sessions and logs under `%LocalAppData%\Grably\`. Outputs default to `Pictures\Grably` and `Videos\Grably`, named `Grably_yyyy-MM-dd_HH-mm-ss`. Give the Velopack package an id (for example `SBLAdvisory.Grably`) whose install folder cannot collide with the data folder - verify where Velopack installs.
- **App model.** Single instance (named mutex + pipe to forward a second launch), lives in the tray, custom `Program.Main` (needed for Velopack), main window is the Library.
- **Privacy.** No telemetry. Keystrokes from the keyboard hook are only ever drawn into video frames, never logged or stored.

### Component design

#### 1. Shell, tray, hotkeys, settings
- Tray menu: Capture region, Capture window, Capture full screen, Scrolling capture, Capture text, Record screen, Open library, Settings, Check for updates, Exit. Tray icon switches to a recording state.
- Global hotkeys via `RegisterHotKey` (with `MOD_NOREPEAT`) on a message-only window. Defaults, all rebindable: `PrintScreen` region, `Ctrl+PrintScreen` full screen, `Alt+PrintScreen` active window, `Ctrl+Shift+PrintScreen` scrolling, `Ctrl+Alt+T` capture text, `Shift+PrintScreen` start/stop recording, `Ctrl+Alt+P` pause/resume (registered only while recording). When registration fails (Windows 11 can reserve PrintScreen for Snipping Tool) show the conflict in Settings with a button that opens `ms-settings:easeofaccess-keyboard`.
- Settings (versioned JSON with migration): hotkeys, save folders, after-capture action, image format, include cursor in screenshots, capture delay, recording fps / resolution cap / quality, audio devices, countdown, cursor-effect and webcam defaults, start with Windows (HKCU Run), theme, last-used style per editor tool.

#### 2. Screenshot capture
- On trigger, grab the whole virtual desktop once with GDI `BitBlt` (`CAPTUREBLT`) into a frozen bitmap, then show one borderless topmost overlay window **per monitor** displaying that monitor's part of the frozen image at 1:1 device pixels. Never span one WPF window across monitors with different DPI; position each with `SetWindowPos` in physical pixels after `SourceInitialized`.
- Selection state is shared across overlays in virtual-desktop pixels; each overlay draws its own intersection, so a drag can cross monitors.
- Overlay features: dimmed surround, drag to select, resize handles, size label, magnifier loupe with pixel grid + coordinates + hex colour, arrow keys nudge by 1 px, Enter/double-click confirm, Esc/right-click cancel, hover window-snap (top-level windows in z-order via `EnumWindows`, bounds from `DWMWA_EXTENDED_FRAME_BOUNDS`, skip cloaked/minimised/own windows) so a click captures that window.
- The same overlay is reused with a mode flag for Screenshot, Record target, Capture text and Scrolling capture.
- Full-screen and active-window hotkeys skip the overlay and crop the frozen bitmap directly. Record the foreground window title and process name with each capture for the library.
- Result: clipboard gets the image (PNG stream plus standard bitmap format), file saved, library item created, editor opened - per the after-capture setting.

#### 3. Annotation editor
- **Model (Core, WPF-free, JSON-serialisable with `System.Text.Json` polymorphism):** `AnnotationDocument { Version, BaseSize, Crop?, Items[] }`. Item types: Arrow, Line, Rectangle, Ellipse, Pen (freehand), Highlighter, Text, Step (auto-incrementing numbered badge), Blur, Pixelate. Geometry is in base-image pixel coordinates; z-order is list order.
- **Rendering (App):** one `AnnotationRenderer` draws any item to a `DrawingContext`. The on-screen layer (a custom `FrameworkElement` with one `DrawingVisual` per item inside a zoom/pan host) and the flattened export (`DrawingVisual` -> `RenderTargetBitmap` at image pixel size, 96 DPI) both go through it, so export always matches the screen. Blur/Pixelate compute a cached bitmap from the base image pixels under their rect.
- **Interaction:** tool strip (Select, Arrow, Line, Rectangle, Ellipse, Pen, Highlighter, Text, Step, Blur, Pixelate, Crop), contextual property bar (colour swatches + hex + recent colours, thickness, opacity, fill, font, size, shadow), selection handles, move/resize, endpoint drag for arrows and lines, Shift to constrain, in-place `TextBox` for text editing, z-order, duplicate, copy/paste, delete, nudge, Ctrl+wheel zoom, Space-drag pan, fit/100%.
- **Undo/redo:** snapshot-based - after each completed gesture push the serialised item list (documents are tiny). Simple and hard to get wrong.
- **Crop:** non-destructive `Crop` rect on the document; export applies it; "Reset crop" restores.
- **Commands:** Copy, Save (overwrites the flattened library file), Save as PNG/JPG, Copy text (OCR), open image file, paste image from clipboard as a new document, drag the result out to other apps.
- **Re-editable projects:** each screenshot keeps a sidecar zip `%LocalAppData%\Grably\projects\{id}.grably` containing `original.png` and `document.json`. The library file is the flattened render.
- Default look: red stroke, 4 px, soft shadow. Shortcuts: V A L R E P H T N B X C, Ctrl+Z/Y/C/V/S/D, Delete.

#### 4. Library
- SQLite at `%LocalAppData%\Grably\library.db`, schema versioned with `PRAGMA user_version`. Table `items` (id, kind screenshot|recording|gif, file_path, project_path, thumb_path, title, source_app, created_utc, width, height, duration_ms, bytes, ocr_text) plus an FTS5 table over title, source_app, ocr_text.
- Library window (WPF-UI `FluentWindow`): filters All / Screenshots / Recordings / GIFs, search box, thumbnail grid (WPF has no built-in virtualizing wrap panel - use the `VirtualizingWrapPanel` package or incremental paging), capture buttons in the header.
- Item actions: open (screenshot -> editor, recording -> trim editor), copy, copy path, show in Explorer, rename, delete to Recycle Bin, drag out as a file. Items whose file vanished are flagged and can be purged.

#### 5. OCR
- `Windows.Media.Ocr.OcrEngine` from user profile languages; if unavailable, explain how to add a language OCR capability. Respect `OcrEngine.MaxImageDimension` (tile or scale), upscale small regions 2x before recognition, keep line breaks.
- Three uses: "Capture text" (region -> text on clipboard -> small confirmation popup), "Copy text" in the editor, and background indexing of every screenshot into `ocr_text` for library search (setting, default on).

#### 6. Scrolling capture
- User picks the scrollable region. Loop: capture the region (GDI), send wheel input at the region centre with `SendInput`, wait until two consecutive captures are identical (or 500 ms), capture, stitch. Start with one notch, measure the offset, then adapt the notch count so each step moves about half the region height.
- `ScrollStitcher` lives in Core as pure code: detect static header/footer bands shared by consecutive frames, find the best vertical overlap, append only new rows. Exact whole-row hashes will not match in practice (the scrollbar thumb moves every frame and hover states change), so match on a central column band that excludes the right-hand scrollbar strip, with a small per-pixel tolerance and a minimum-confidence threshold. Unit-test it with synthetic tall images (with and without a sticky header, with repeated rows, with a moving scrollbar drawn in).
- Stop on: no movement twice in a row, Esc, Stop button, or 30,000 px height. Result goes through the normal after-capture flow. Document it as best effort (lazy-loading pages and animated content can defeat it).

#### 7. Recording engine (Platform)
Pipeline: **Windows.Graphics.Capture -> D3D11 compositor at fixed fps -> readback -> ffmpeg stdin -> intermediate file -> mux with audio -> MP4.**
- **Capture:** `GraphicsCaptureItem` for a monitor or window through `IGraphicsCaptureItemInterop`, `Direct3D11CaptureFramePool.CreateFreeThreaded`, `IsBorderRequired = false`, cursor drawn by WGC. A region is a monitor capture plus a crop (for recording, clamp the region to one monitor). Handle window resize (`Recreate` the frame pool when `ContentSize` changes, scale/letterbox into the fixed output size), minimised windows (no frames arrive - keep repeating the last frame) and window close (stop cleanly). Call `ID3D11Multithread.SetMultithreadProtected(true)` because frame-pool callbacks and Direct2D share the device. Inside `FrameArrived`, copy the frame into a texture the engine owns and dispose the frame immediately. Whether an unpackaged app must call `GraphicsCaptureAccess.RequestAccessAsync(Borderless)` is unclear (verify): call it, ignore the result, and assert in a harness test that the captured frame has no border pixels.
- **Compositor:** dedicated thread ticking at the target fps (30 default; 15/60 optional) from one `Stopwatch` clock shared with audio. Each tick draws onto an output texture with Direct2D: latest captured frame (cropped/scaled), then cursor highlight, click ripples, keystroke pill, webcam bubble. Animations advance even when the screen is static. Output width and height are forced even.
- **Encoding:** read the composed frame back through a staging texture (respect `RowPitch`) and write raw frames to ffmpeg's stdin as constant frame rate: emit frame N when the clock passes N/fps, duplicating or dropping to stay on the clock. A bounded queue separates compositor and pipe writer so a slow encoder never blocks capture.
- **Pixel format is a parameter of the frame sink from day one.** Benchmarks on this machine showed the limit is ffmpeg's CPU colour conversion, not the pipe: piped BGRA managed about 89 fps at 3440x1440 and 46 fps at 4K, piped NV12 about 167 and 107 fps. So: build the BGRA path first (it stays as the fallback where no video processor exists, such as VMs), then in the same milestone add GPU BGRA -> NV12 conversion with `ID3D11VideoProcessor` before readback and make it the default. Gate it with a DevCli `bench` command that reports achieved fps and dropped frames, and assert colour values from an extracted frame of a known test pattern to catch colour-range mistakes. Do not use a Media Foundation SinkWriter: it is not crash-safe by default and much harder to debug headlessly.
- **Encoder choice:** order `h264_nvenc`, `h264_qsv`, `h264_amf`, then software `h264_mf`, then `libopenh264`. Never `libx264` (absent from the bundled LGPL build). An encoder being listed proves nothing - this Intel-only machine lists nvenc and amf - so probe with a short real encode **at the actual output size** and cache the result per size. H.264 NVENC rejects widths above 4096 (a 5120-wide monitor fails): on failure fall back to the next encoder, then to `hevc_*`, then to downscaling. Take exact rate-control flags from `ffmpeg -h encoder=<name>`, not from memory. Keyframe every 1 s so trim preview seeks well. `yuv420p` output for player compatibility.
- **Crash safety:** encode to a crash-tolerant intermediate (MKV) in `%LocalAppData%\Grably\sessions\{id}\` beside a `session.json`. On startup, offer to recover unfinished sessions.
- **Audio:** NAudio WASAPI loopback (system) and capture (mic), each written to its own file with its start offset on the shared clock. Write raw PCM plus a small format sidecar, not WAV (WAV headers are left unfinalised by a crash and hit the 4 GB limit on long multichannel recordings). Sample count is not a clock: per packet, compare cumulative samples with the shared `Stopwatch` and pad silence when the stream falls behind by about 20 ms (this also covers loopback delivering nothing during silence; rendering silence to the device is an optional extra). At mux time correct each track by its measured samples-per-elapsed-second ratio to remove drift. Reopen capture when the default device changes mid-recording (`MMDeviceEnumerator` notification client). Mic mute writes silence. On stop, one ffmpeg pass does video stream-copy + `amix` of the offset-aligned tracks -> AAC -> MP4 with `+faststart`. NAudio 3 changed this API surface (`WasapiCapture`/`WasapiLoopbackCapture` are marked obsolete in favour of `WasapiRecorderBuilder`, events fire per WASAPI packet) - read its 2-to-3 migration guide before writing this.
- **Pause/resume:** freeze the frame clock and discard audio for the paused interval.
- **State machine:** Idle -> Countdown -> Recording <-> Paused -> Finalizing -> Completed | Failed, with progress events for the UI.
- **ffmpeg:** bundle the win64 `lgpl-shared` build from FFmpeg-Builds (the BtbN repo now redirects to `FFmpeg-Builds/FFmpeg-Builds`); the shared variant is roughly half the size of the static exe. Daily builds are deleted after 14 days and `latest` changes daily, so pin a month-end build (kept for two years) by exact URL + SHA256 in `tools/fetch-ffmpeg.ps1`, or mirror that zip as a release asset in the Grably repo. Never commit the binaries. Resolution order: bundled -> explicit settings override. PATH is used only when `GRABLY_FFMPEG_ALLOW_PATH=1` is set; tests, DevCli checks and CI always run against the bundled build, because the PATH build here is GPL with libx264 and would hide encoder mistakes. One `FfmpegRunner` handles process start, stderr capture to the log, `-progress pipe:1` parsing and cancellation.

#### 8. Recording UX (App)
- Start: overlay in Record mode (drag a region, click a window, or click a monitor) -> pre-record bar with toggles for system audio, microphone (level meter), webcam, cursor effects, keystrokes, fps -> Record -> 3-2-1 countdown (can be disabled).
- During: thin frame around the region, floating control bar (timer, pause/resume, stop, mic mute, discard), optional webcam bubble. All of these windows call `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` so they never appear in the video. Whether that works on WPF `AllowsTransparency` (layered) windows is unconfirmed (verify): make it the first harness test of the milestone - show the chrome, capture a frame, assert it is absent. If it fails, build the chrome from non-layered windows (opaque bar, frame made of four thin opaque windows).
- Stop: finalise, save to `Videos\Grably`, add to library, open the trim editor.
- **Cursor effects:** `WH_MOUSE_LL` and `WH_KEYBOARD_LL` installed only while a recording with effects is running, on a thread with a message loop, with the delegates kept alive in fields. Highlight = translucent disc under the pointer position at frame time; click = expanding ring (different colour for right click); keystrokes = pill at bottom centre. Defaults: highlight on, clicks on, keystrokes off, with keystroke mode "shortcuts only" unless the user chooses "all keys".
- **Webcam:** WinRT `MediaCapture` + `MediaFrameReader` (pick a format up to 720p30, BGRA). One `WebcamSource` holds the latest frame; the on-screen bubble window (draggable, mirrored, circle or rounded rectangle, three sizes, excluded from capture) shows it, and the compositor draws the same frame at the bubble's position relative to the capture rectangle. Clear error when camera access is denied.

#### 9. Trim editor and export
- Preview: WPF `MediaElement` for playback only (play/pause, speed). It cannot frame-step and gives no seek-completed signal, so whenever the user is paused, scrubbing or stepping, show an image of the exact frame decoded by ffmpeg at `N/fps` (debounced, cached) instead of the `MediaElement` surface. The 1-second keyframe interval keeps those decodes fast.
- Timeline: ffmpeg-generated thumbnail strip and waveform image, playhead, draggable start/end handles, "Cut selection" to remove a middle range, undo/redo. Playback skips removed ranges.
- `EditList` (Core, pure, unit-tested): kept segments -> ffmpeg `filter_complex` (`trim`/`atrim` + `setpts`/`asetpts` + `concat`). v1 always re-encodes for frame accuracy, using the probed encoder, with a progress dialog and cancel.
- Export targets: MP4 (source / 1080p / 720p, quality preset) and GIF (`palettegen` + `paletteuse`, fps and width presets). "Save frame as image" sends the current frame to the screenshot editor. Exports become new library items; the original recording and its edit list (sidecar JSON) are kept so trimming can be reopened.

#### 10. Packaging, updates, release
- `dotnet publish -c Release -r win-x64 --self-contained`, then Velopack `vpk pack` with the app icon; ffmpeg is included in the package.
- `Program.Main`: `VelopackApp.Build().Run()` first, then single-instance check, then host + WPF app. Update check in the background at startup and from Settings/tray, using the GitHub Releases source for `SBL-Advisory/grably`; prompt to restart when an update is ready.
- `release.yml` on tag `v*`: restore, build, test (non-Desktop), fetch ffmpeg, publish, `vpk download github` (needed so deltas can be built), `vpk pack`, `vpk upload github --publish`. `ci.yml` on PRs: build + unit tests.
- Binaries are unsigned at first: README explains the SmartScreen prompt. Add LICENSE (MIT) and THIRD-PARTY-NOTICES.md (ffmpeg LGPL text, the exact build and source link, NuGet licenses). Follow-ups to list in the README roadmap: free OSS code signing (SignPath Foundation) or Azure signing, winget manifest.

### Pitfalls to design around

- Mixed-DPI multi-monitor setups are the top source of capture bugs: keep everything in physical pixels and test with `--ui-snapshot` plus DevCli numbers.
- Low-level hook delegates get garbage collected unless stored in fields; hook callbacks must return quickly.
- WASAPI loopback delivers nothing during silence, and capture formats differ per device - resample to one format before mixing.
- ffmpeg stdin pipes: always drain stderr on another thread or the process deadlocks; close stdin to finish the file.
- Width/height must be even for `yuv420p`.
- `RenderTargetBitmap` and WPF bitmap work must run on an STA thread (tests included).
- Bundle only an LGPL ffmpeg build. The PATH build on this machine is GPL with libx264, so `-c:v libx264` would pass locally and fail for users - never reference it.
- Overlay, region-frame and control-bar windows are plain `Window`s, not WPF-UI windows. Use WPF-UI theming only; do not also set the built-in `ThemeMode` (still experimental, WPF0001).
- GDI screenshots of HDR monitors come out washed out. v1 documents this as a known limitation in the README.
- GitHub-hosted runners have no usable interactive desktop for WGC - keep `Category=Desktop` tests out of CI.

### Verification

Per milestone: `dotnet build -warnaserror`, `dotnet test --solution Grably.slnx --filter-not-trait "Category=Desktop"`, the DevCli checks in the milestone table, then `Category=Desktop` tests locally.

DevCli commands to build as the features land: `screenshot`, `windows`, `monitors`, `render`, `ocr`, `stitch`, `encoders`, `bench`, `record` (`--monitor|--window|--region`, `--seconds`, `--fps`, `--system-audio`, `--mic`, `--webcam`, `--cursor-fx`, `--keys`), `synctest`, `export` (`--keep a-b,c-d --format mp4|gif`), `library`.

End-to-end before the first release tag: install from the generated Setup exe on this machine; take region, window, full-screen and scrolling captures; annotate with every tool, save, reopen from the library and confirm annotations are still editable; capture text; record a region with system audio, mic, webcam and cursor effects, pause and resume, stop; trim both ends, cut a middle section, export MP4 and GIF and play both; publish a higher test version and confirm the installed app updates itself.

### Out of scope for v1

Multi-track timeline, transitions, zoom-and-pan, video annotations, callout/speech-bubble shapes, cloud upload and share links, ARM64-native build, localisation (keep UI strings in resources so it can be added), HDR-correct capture, code signing.
